# 开发问题记录与规避清单

> 本文档汇总本项目开发过程中遇到过的所有问题、根因与解决方案，
> 并沉淀为后续开发的强制性规避规则。**每次改动前先看「规避规则」。**

---

## 一、问题汇总

### 1. 脚本与部署

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|
| 1 | 双击 `deploy.bat` 窗口一闪就关 | `$ErrorActionPreference = "Stop"` 下，原生命令（`gh auth status`）向 stderr 输出即触发致命错误，脚本在开头就退出；且 `.bat` 末尾无 `pause` 兜底 | 错误策略改 `Continue`，用 `$LASTEXITCODE` 判断；`.bat` 末尾加 `pause`；`Fail()` 显式退出 |
| 2 | `git push` 报 `couldn't create signal pipe, Win32 error 5` | 受限环境限制 Git for Windows 的 MSYS 运行库创建信号管道（非项目问题） | 在正常终端执行 push；SSH 密钥已验证有效 |
| 3 | 提交作者是占位身份 `game-guide@local` | 本地无 git 身份配置 | 部署脚本用 `gh api user` 取真实账号，自动 `git commit --amend --reset-author` |
| 4 | `.ps1` 中文乱码 / 解析报错 | 文件为 UTF-8 无 BOM，Windows PowerShell 5.1 按 ANSI 读取导致乱码和花括号误判 | 所有 `.ps1` 保存为 **UTF-8 带 BOM**；**每次编辑后必须重加 BOM 并校验** |

### 6. 数据正确性（最值得警惕的一类）

| # | 问题现象 | 根因 | 解决方案 |

### 7. 功能实现（第二轮优化发现）

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|
| 18 | 水稻收益算出 `NaN` | `data.js` 中 `rice.growth` 是字符串 `"6-8"`（水稻近水可提前 2 天成熟），算术运算 `28 - "6-8"` 得 `NaN`，NaN 会沿着排序比较器污染整个列表顺序 | 新增 `cropGrowthDays()` 容错解析：数字直接用，区间取**上限**（偏保守）；显示仍保留原文 `"6-8 天"`，不丢失信息 |
| 19 | **霜瓜永远无法通过筛选触达** | 农作物筛选栏硬编码 `春/夏/秋`，而数据里已有 3 种含冬季的作物（霜瓜、茶叶、齐瓜） | 抽出 `CROP_SEASON_FILTERS` 常量并补「冬」；新增断言「数据中出现过的季节必须有对应筛选按钮」，杜绝同类漏配 |
| 20 | 搜索跳转"跳了个空"：搜到的条目没被高亮 | `focusItem()` 只切换模块，不清空该模块**已有的筛选条件**——在「海洋」筛选下搜河流鱼，卡片根本不在 DOM 里 | 抽 `FILTER_RESET` 映射，跳转前先重置该模块筛选并重渲染 |
| 21 | 筛选后标题仍写「共 46 条」，用户以为筛选失效 | `setCount()` 传的是**全量长度**而非筛选结果数 | 新增 `setShown()` 输出「当前显示 N 条」，与总数并列显示；`#xxxCount` 保持总数不变，兼容既有断言 |
| 22 | **3 张贴图（cave-grub / gold-slime / iridium-slime）反复重跑下载脚本也补不上** | `download-images.ps1:337` 的兜底映射 `$pageNames` 只在 `$items[$e.Key]` 存在时才会被查询，而这 3 个 id **只写在 `$pageNames` 里、从未进入主下载列表 `$items`** → 该兜底分支对它们是**死代码**，永远不触发。脚本报「失败 0 个」是因为压根没尝试 | 待修：把 3 个 id 按真实 Wiki 文件名补进 `$items`（依 R12 先验证存在性）。当前用自绘 SVG 兜底图标，不影响使用 |
| 23 | 部署脚本在沙箱受限模式下**完全跑不通**：`index.html`/`.git` 写入被拒、`ssh` 报 `couldn't create signal pipe, Win32 error 5` | 两道**互相独立**的墙：①沙箱对 `.git` 等路径的写入拦截；②受限模式下进程无法创建命名管道，而 Git for Windows 的 MSYS 运行库需要它。**这不是项目缺陷** | 对本机部署命令做**一次性提权**（full access）后一次通过：bump 版本、自检、贴图下载、提交、推送全部成功，Actions 26s 完成。见 R20 |
| 24 | R15 的判断有偏差：以为 PowerShell 连不上 Wiki 是 schannel 限制 | 实为**沙箱拦截**。完全权限下 `download-images.ps1` 原样跑通（220 项全部命中、失败 0） | 已修正 R15：脚本本身没问题，缺的是权限 |

### 9. 内容完备性（第四轮审计发现）

> 结论：**存在性可靠，完备性不足**。9 个模块里 3 个已完整、4 个有小缺口，但另有 **10 个整块游戏系统完全没有覆盖**。

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|
| 30 | **存在性审计自身有覆盖盲区**：声称"全部条目已核对"，实际只覆盖 231/313 条（73.8%），82 条从未验证过 | ①`verify-wiki.js` 依赖手工维护的英文映射表 `EN`，数据里新增的中文条目常忘记补映射，脚本只打印一行 ⚠️ 就跳过；②QUESTS(10) 与 EVENTS(12) **完全没纳入映射表与审计范围** | 改为**双轮核对**：第一轮用中文名直查中文 Wiki（无需映射表，覆盖全量 313 条，实测 89.5% 命中）；第二轮保留英文交叉验证。新增数据自动进入审计，不再依赖人工补表 |
| 31 | **从没有过完备性审计**：工具只回答"我们收录的是否真实"，从不回答"游戏里有的我们是否漏收" | `verify-wiki.js` 是单向的（data → wiki），缺少反方向（wiki → data）的差集能力；且从未有人把 Wiki 分类全集拉下来比对 | 新增 `test/audit-completeness.js`：拉取中文 Wiki 分类全集做双向差集。首轮实测 —— 逐模块缺 **59 项**（收集物 10 / 采矿 24 / 战斗 14 / NPC 10 / 农作物 1），另有 **10 个整块系统**未覆盖：烹饪 82、打造 90、工匠制品 35、果树 9、动物 13、武器 69、种子 70、古物 43、建筑 57、工具 24 |
| 32 | 审计时先用**英文** Wiki 分类做比对，结果 `Category:Crops` 只返回 5 项 | 星露谷 Wiki 的英文分类是`Category:Crops`这种"容器类"，真实内容散在 `Spring crops`/`Vegetables` 等子类；中文 Wiki 反而是干净的**中心类**（`农作物`按季节分、`鱼`、`怪物`、`NPC` 都是直接成员） | 完备性比对统一以**中文 Wiki 分类**为准；并注意排除同名分类页（`鱼`、`怪物`、`矿石`这类既是分类又是条目） |
| 33 | 首次统计"无英文映射"得出 139 条，实际只有 60 条 | 统计脚本的正则 `([a-z0-9-]+)\s*:\s*"` 无法匹配**带引号的键**（`"blue-jazz": "Blue Jazz"`，键后先有引号再有冒号），把 79 个带连字符的键全部漏掉了 | **统计脚本本身也要被验证**：数字异常时先怀疑统计口径。改用直接按 `EN[mod][id]` 查表，由数据侧驱动计数 |

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|

| 35 | `cave-grub`（蛆）英文页名错误，且数值全错（HP 25/伤害 6/矿井 1-39 层） | 真实怪物叫 **`Grub`**，信息框权威值为 **HP 20 / 伤害 4 / 矿井 15-29 层**、掉落含虫肉 60%/古代种子 0.5%/白色藻类 2%/稻芽 10% | id 正名为 `grub`，数值与掉落按 Wiki 信息框修正 |
| 36 | `gold-slime`（金史莱姆）数值与掉落均错（HP 500/掉落"黄金矿石"） | 金史莱姆是**0.1% 概率替换任意史莱姆**的变异，**继承本体全部属性**，额外必掉至少 1 枚 250 金币；Wiki 无独立条目页也无图片 | 数值改用 `0` 表示"随本体"（渲染层新增 `monsterStat()` 显示为"随本体"），掉落改为金币；贴图走 SVG 兜底 |

### 12. 架构重构（第六轮：模块注册表）

> 起因：9 个模块全部**按物品类型**切分，站内已有 50 条「采集包」引用无处可去。要加第 10 个模块（社区中心收集包）时发现——「一个模块」被写死在 5 处，加模块必漏配。

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|
| 39 | 删改 `js/main.js` 的一整段（137 行）时，**DSH 文件工具无法按行区间删除**，而 PowerShell / Python 写该项目目录一律 `PermissionError` | 双重限制叠加：①`edit` 是字面量替换工具，删 137 行需要把全文抄进 `old_string`，不可靠；②项目在会话工作区（`D:\deepseek`）**之外**，沙箱禁止派生进程写入，且该拦截来自**沙箱策略而非 ACL**（#26 已证） | 对**那一条精确命令**做一次性提权（`danger-full-access`）执行「脚本放工作区内、只写项目文件」的行区间拼接，之后照常回归自检。**判据**：`[sandbox: file access denied under workspace-write mode]` + 提示 `escalation available` 即为此情形，不要反复换写法硬试 |
| 40 | 贴图覆盖率报告从「331/332」**跳变成「331/366」**，多出 34 个"缺失贴图"（全是任务/节日/事件条目） | 重构时把「模块清单」改为数据驱动，顺手把**所有**模块的条目都算进了贴图分母——但任务/节日/事件在 UI 上用 emoji 呈现，**本就没有贴图**，不是缺口 | 分母只统计**显式声明了贴图命名前缀**的模块。**教训：重构统计口径时，先看清原口径的语义边界**（原报表只覆盖 6 个贴图模块），否则一个"更通用"的写法会把噪音当缺口报出来 |
| 41 | 修 #40 时改用 `if (!sec.spriteFor) continue;` 判断，覆盖率**再次错成 48/48**（只算了 NPC） | `spriteFor` 对物品类模块取值是**空字符串**——`""` 是合法前缀（`img/<id>.png`）却 falsy，真值判断把 5 个物品模块全部过滤掉了 | 判据必须是**「属性是否存在」**（`hasOwnProperty`）而非**「值是否为真」**。同型陷阱：`0`、`""`、`NaN` 这类"合法的假值"在配置表里一律要用显式判存 |

### 13. 收集包模块（第七轮：首个"按玩家目标"组织的模块）

> 数据全部来自中文 Wiki「收集包」页的 wikitext 解析（31 包 / 7 房间 / 130 需求项），配合 `Module:Items` 的中英名表做名称对齐。过程中踩到的坑如下。

| # | 问题现象 | 根因 | 解决方案 |
|---|---------|------|---------|
| 42 | 用 `titles=英文名` 查中文 Wiki **全部报"不存在"**；改用中文条目名查 `langlinks` 只拿到 **90/365**；再试英文 Wiki 反查中文 langlinks 只有 **40/146**；全文搜索英文名 **零结果** | 中文 Wiki 的 2373 个条目**多未挂跨语言链接**，且**不索引英文名**（星露谷 Wiki 靠 `{{Name}}` 模板 + `Module:Items` 名表做英中映射，不走页面标题） | 找到权威来源：`{{Name}}` 由 `Module:Items` 渲染，该模块用 **item id 串联**中英名表（`en/name/ids` + `zh/ids/name`）。拉下这两张表即得**完整映射**：146/146 全部解析成功。**教训：先找数据源的真实机制，再决定实现路径**——前面四条路都是在猜"Wiki 大概怎么存名字" |
| 43 | 收集包需求项里出现 `"大鸡蛋\|棕色大鸡蛋"`，被当成一个物品名 | wikitext 用**转义竖线**表达「二者之一」（`{{Name|大鸡蛋\|棕色大鸡蛋}}`），按普通竖线切分会把它拆成两个物品；另有 `{{Name|Wood\|99}}` 这种**转义竖线 + 数量**混排 | 解析 `{{Name}}` 时先按**未转义竖线**切参数，再对每个参数按 `\|` 展开为多选槽；数量只认**末尾的纯数字参数**。同时保留「多选槽 + 同名单槽」的**合并逻辑**（游戏里是同一个格子） |
| 44 | 「任选 5 / 共 9 项」的包**永远判不出「已完成」** | 把「物品总数」当成了「需要提交的格数」——`bundleSlots` 返回 9，而玩家只需交 5 格，`filled >= slots` 永不成立 | 拆成两个函数：`bundleNeeded`（需交格数 = `choose \|\| 物品数`）与 `bundleSlotCount`（可选物品总数）。**「有多少选项」与「要交几格」是两个概念**，混用会让进度判定静默失效 |
| 45 | 勾选后**界面显示已勾选、进度却算作 0**；且取消勾选时进度数组已空但计数仍是 1 | 两个独立缺陷叠加：①`dataset.slot` 取回的是**字符串** `"0"`，被 `Number.isInteger` 过滤器整条丢掉；②`bundleProgress(id)` **只接受 id**，传入包对象时查不到 key 而静默返回 `[]` | ①读进度时用 `Number(x)` 归一化下标并用 `indexOf` 去重（**兼容历史脏数据**）；②`bundleProgress` 同时接受 id 与包对象。**教训：接受"静默返回空"的函数极其危险**——它把类型错误伪装成"没有数据"，界面与进度还能各说各话 |
| 46 | 调试时反复看到自相矛盾的输出（同一时刻 `progress=[]` 又 `filled=1`） | 把**不同时点**的取值拼进一条日志（模板字符串先于断言求值、`store` 与函数读取的时刻不同），误判为幽灵 bug，多花数轮排查 | 排查状态矛盾时，**要么一条日志只取一个时点**，要么把快照变量全部先算出来再拼接。另有收获：与其在巨型测试文件里加日志，不如**写一个最小复现脚本独立跑**——本项目最终就是靠它一眼定位到"对象当 key"这个真因 |

## 二、规避规则（后续开发必须遵守）

| 编号 | 规则 |
|------|------|
| R1 | **模板 id 与查询 id 必须一致**：写完渲染函数后，grep 核对 `${m.id}Count` 与所有 `#xxxCount` 引用 |
| R2 | **DOM 查询一律空值安全**：可能为 null 的元素用 `if (el)` 或 `setCount()` 模式，绝不裸调 `.textContent` |
| R3 | **每次发布 bump 版本号**：`index.html` 的 `?v=N` 必须 +1，否则浏览器缓存会出幺蛾子 |
| R4 | **发布前必须跑冒烟测试**：`node test/smoke.js`（已集成进 `deploy.bat`，失败自动中止部署） |
| R5 | **改过任何 `.ps1` 后必须重加 UTF-8 BOM** 并用解析器校验语法。注意：**通用文本编辑工具会静默剥离 BOM**（#37），所以每次编辑后都要重新校验，不能假设它还在。最快诊断：按 UTF-8 显式读入再 `ParseInput`，通过即说明是编码问题而非语法问题 |
| R6 | **批量外部 API 调用前查平台限制**（如 MediaWiki `titles` ≤ 50/次），超限必须分批 |
| R7 | **对接外部 API 先确认返回格式的规范化行为**（大小写、空格/下划线、转义） |
| R8 | **部署后验证线上**：核对线上文件与本地一致、资源 200、渲染无报错（用 `test/verify-online.js` 思路，或 Node fetch 抽查） |
| R9 | **GitHub 基础设施错误先重试**（429 / 构建失败），不要急着重构代码 |
| R10 | **复杂脚本写文件执行**，避免内联命令被 shell 转义破坏；jq 表达式保持纯 ASCII |
| R11 | **数据字段先定义后使用**：给数据加新字段（如 `locCat`）时，确保所有渲染/筛选逻辑同步更新，并跑数据完整性校验（id 唯一、必填字段齐全） |
| R12 | **新增数据必须验证存在性**：任何新物品/怪物/NPC，先用 Wiki 搜索/`allpages` API 确认条目真实存在，杜绝凭记忆编造（已因此误收录 4 个不存在的条目） |
| R13 | **文件名不手工猜**：贴图/图片一律用 `pageimages` API 按英文条目名取真实 URL（如 Tigerseye、Star Shards），不按 `ItemName.png` 惯例脑补 |
| R14 | **持续失败先怀疑数据**：某条目反复下载失败，第一反应查"它是否真的存在于游戏/Wiki"，而不是反复改文件名映射 |
| R15 | **能用 Node fetch 直连外部源就自己做**：受限模式下 Node fetch（undici/OpenSSL）可访问星露谷 Wiki，而 PowerShell 的 `Invoke-RestMethod`/`Invoke-WebRequest` 报「基础连接已经关闭」——**该限制来自沙箱，而非 schannel**（#24 已证伪原判断：完全权限下 `download-images.ps1` 原样跑通、220 项全部命中）。用 Node 脚本下载与验证可减少对权限的依赖 |
| R16 | **参与算术的字段必须是数字**：数据里混入 `"6-8"` 这类区间字符串会让 `NaN` 沿排序/聚合静默扩散（排序结果整体失效却不报错）。进入计算前一律经容错解析函数转换，区间取保守端 |
| R17 | **新增数据分类必须同步补筛选入口**：数据中出现新季节/新水域/新类型时，筛选常量必须同步扩充，否则内容「存在但不可达」；`check.js` 已加断言自动拦截 |
| R18 | **跳转前先清空目标模块的筛选**：任何「从 A 跳到 B 条目」的路径都要先重置 B 的筛选并重渲染，否则目标条目可能被筛选条件挡在 DOM 之外，高亮落空 |
| R19 | **能进程内验证就不要依赖外部浏览器**：本沙箱中 Chrome/Edge 无头模式因 mojo 需要命名管道而无法启动（`platform_channel.cc: Check failed`），视觉验证需用户人工确认；**交互逻辑应在 `check.js` 内用合成事件直接驱动真实处理器**（见第 5 节），不依赖浏览器 |
| R20 | **本机跑 `deploy.bat` 需要完全权限**：沙箱受限模式下 `.git` 写入与 `ssh` 命名管道两道墙都过不去（#23），表现为「版本号没变、没有任何提交、推送失败」。这**不是脚本缺陷**，别去改脚本；用一次性提权执行，或由用户在普通终端双击 `deploy.bat`。另注：每次失败都是**空操作**（不产生半成品提交），可放心重试 |
| R21 | **临时文件必须清理，且要有断言兜底**：`deploy.bat` 会 `git add -A`，根目录遗留的预览/调试文件会被一起提交上线。临时文件一律用 `_` 前缀命名，`check.js` 已加断言「根目录无 `_` 开头文件」，自检失败会直接中止部署（本轮已实测拦住一次） |
| R22 | **视觉改动先截图再发布**：界面类改动不能只靠审阅代码。截图时必须在预览页禁用 CSS 动画，否则 `--virtual-time-budget` 截到淡入中途，会把正常样式误判为失效 |
| R23 | **图标尺寸取源图的整数倍或整数分之一**：48px 贴图按 1:1、128px 立绘按 1/2 呈现，避免非整数缩放造成像素错位。这条对像素画清晰度的影响**大于** `image-rendering` 属性本身 |
| R24 | **正确的算法也要检查呈现**：算出负数、极值、0 这类"对但反直觉"的结果时，必须给出视觉区分或成因说明，否则用户会当成 bug（向日葵负收益即此例） |
| R25 | **存在性审计必须以「无需人工维护映射」的方式覆盖全量**：任何依赖手工映射表的核对，都会随数据增长而静默失守（#30 的 82 条盲区就是这么来的）。本项目统一用**中文名直查中文 Wiki**，新增数据自动纳入 |
| R26 | **定期跑完备性审计**：`verify-wiki.js` 只防编造，防不了遗漏。每次成批补内容后跑 `node test/audit-completeness.js`，对照 Wiki 分类全集看差集（#31） |
| R27 | **对外的比对口径先验证再下结论**：分类型数据在 Wiki 上的组织方式各家不同（英文是容器类、中文是中心类），拿错口径会得出"Wiki 只有 5 种作物"这种荒谬结论（#32） |
| R28 | **统计脚本的数字先自证再用**：算出的指标异常时（如"139 条无映射"），第一反应是查统计口径而非直接写进结论（#33） |
| R29 | **判伪要看三处，判真只需一处**：某条目若在①Wiki 汇总页、②权威分类名录、③图片文件三处**全部查不到**，基本可断定是编造（#34 的铱史莱姆即三缺）。反之，**"分类名录里没有"绝不等于编造**——史莱姆/蝙蝠变体、任务、心事件都挂在 `Slimes`/`Bats`/`任务`/`随机事件` 汇总页下，属正常情况，误判会把真内容删掉 |
| R30 | **Actions 报「找不到 github-pages artifact」时先查证再动手**：用 `gh api repos/<owner>/<repo>/actions/runs/<run-id>/artifacts` 确认 artifact 是否真的存在。**若存在即为竞态**（#38 实测 213982 字节确实已生成），用 `gh workflow run pages.yml --ref main` 重新触发即可，**不要改 workflow、不要删重建仓库** |
| R31 | **补完内容后必须跑完备性审计并做到"可解释归零"**：目标不是"数字为 0"，而是**每一项剩余差异都有明确记录的理由**。经核对的排除项写进 `audit-completeness.js` 的 `EXCLUDED` 表（含原因），否则每次审计都会把同一批无关项当成缺口重复排查 |
| R32 | **移动脚本前先把内部路径改好，再整体搬移**：不要"边移动边修改"，否则出错时分不清是路径问题还是改动问题。搬移后必须校验三件事——①`.ps1` 仍是 UTF-8 带 BOM（R5）②语法解析通过 ③根目录推算正确。`.bat` 中 `%~dp0` 会随文件移动而改变，工作目录需显式回退到项目根 |
| R33 | **行区间级的文件手术用「脚本 + 一次性提权」**：DSH 的 `edit` 是字面量替换工具，删除上百行需要把全文抄进 `old_string`，既脆弱又易错；而项目目录在会话工作区之外时，派生进程写入会被沙箱拒绝（#39）。此时对**那一条精确命令**提权执行（脚本放工作区内、只写目标文件），随后立刻回归 `node test/check.js` 验证。看到 `escalation available` 提示就是这个情形，别反复换写法硬试 |
| R34 | **配置表里判别「有没有」要用判存，不能用判真**：`spriteFor: ""` 是合法取值（表示贴图无前缀）却是 falsy，`if (!sec.spriteFor)` 会把所有物品模块误判成"无贴图"（#41 实测把覆盖率错报成 48/48）。空串、`0`、`NaN` 这类**合法的假值**在配置中一律用 `hasOwnProperty` / `!== undefined` 判断 |
| R35 | **改统计口径前先确认原口径的语义边界**：把「模块清单」改成数据驱动时，顺手把所有模块都算进贴图分母，覆盖率立刻从 331/332 变成 331/366，凭空多出 34 个"缺口"（#40）。**更通用的写法未必是更正确的口径**——重构统计类代码时，先问「原来这张报表到底想覆盖谁」 |
| R36 | **对接外部数据源先找\"权威机制\"，别猜存储约定**：查中文 Wiki 物品中文名连试四条路（英文标题直查、中文页 langlink、英文页 langlink、全文搜索）覆盖率分别只有 0% / 25% / 27% / 0%——因为该 Wiki 的名表根本不在页面标题上，而在 `Module:Items` 里用 **item id 串联**（#42）。**判据**：某种查法大面积"查不到"时，先怀疑**数据组织方式**假设错误，而不是继续换查询词 |
| R37 | **\"有多少选项\"与\"要选几个\"必须分成两个量**：收集包的物品数与所需格数在「任选型」里不相等，混用一个 `slots` 会让 `filled >= slots` 永不成立，表现为进度**永远差一截**（#44）。凡是「从 N 个里挑 K 个」的模型，一律显式区分 `total` 与 `needed` |
| R38 | **不要写\"查不到就静默返回空\"的函数**：`bundleProgress(id)` 传入对象时返回 `[]` 而非报错，于是「界面已勾选、进度为 0」两个真相并存且不抛异常（#45）。查询类函数要么**同时兼容两种入参**，要么**显式失败**；空数组必须是"确实没有"，不能是"参数用错了" |
| R39 | **排查状态矛盾时，一条日志只取一个时点**：把不同时刻的值拼进同一句日志，会造出根本不存在的"幽灵 bug"，白烧好几轮（#46）。**更好的做法是写最小复现脚本**：把可疑函数单独跑一遍（本项目 6 行就定位到真因），比在被测系统里加日志快得多 |
